# Backend Integration — Apps Script / Google Sheet / Google Drive

## Architecture

```
┌─────────────────┐        fetch (GET/POST)        ┌────────────────────┐
│   Web App        │ ─────────────────────────────▶ │  Apps Script        │
│  (this repo)      │ ◀───────────────────────────── │  Web App             │
│  html/js/css       │           JSON                │  (appscript/Code.gs) │
└─────────────────┘                                 └──────────┬─────────┘
                                                                  │ reads/writes
                                                                  ▼
                                                     ┌────────────────────┐
                                                     │ Google Sheet         │
                                                     │ 5 tabs: Machine,      │
                                                     │ Specification, Parts, │
                                                     │ Images, Documents      │
                                                     └──────────┬─────────┘
                                                                  │ read directly
                                                                  ▼
                                                     ┌────────────────────┐
                                                     │ AppSheet app          │
                                                     │ (mobile/tablet UI     │
                                                     │  for the team)        │
                                                     └────────────────────┘

Files (photos/PDFs) upload through Apps Script → Google Drive,
and the Sheet stores the resulting Drive URL — never the file itself.
```

**One source of truth**: the Google Sheet. The web app never talks to the
Sheet directly (browsers can't authenticate to Sheets API without exposing
credentials) — it always goes through the Apps Script Web App. AppSheet is
the exception: it's built to read/write Sheets natively, so it connects
straight to the same Sheet with no Apps Script in between. That means a
machine added from AppSheet on a phone shows up in the web Dashboard, and
vice versa, because both ultimately point at the same 5 tabs.

## Google Sheet schema (5 tabs)

> **If you already have a live Sheet:** the `Machine` tab needs one new
> header added — `BCCode` — anywhere in row 1 (column order doesn't
> matter, `Code.gs` looks columns up by header name). Existing rows can
> be left blank in that column.

Create one spreadsheet with these tabs. Row 1 = headers, exactly as named
(Apps Script and AppSheet both key off these names).

**Machine**
| MachineID | Category | Name | Brand | Model | Type | BCCode | Description | CoverImageURL | CreatedAt | UpdatedAt |
|---|---|---|---|---|---|---|---|---|---|---|

- `MachineID` — e.g. `CM-001`, generated by `nextMachineId()` in Code.gs (prefix per category: CM/GR/TM/IM/OT)
- `Category` — one of `coffee`, `grinder`, `tea`, `ice`, `other`
- `BCCode` — free-text internal reference code ("รหัส BC"), optional, no format enforced

**Specification** (one row per machine — the 12 fixed fields from the wizard)
| MachineID | Voltage | Power | Frequency | CoffeeBoiler | SteamBoiler | Pump | Group | PID | Display | Dimension | Weight | WaterTank |
|---|---|---|---|---|---|---|---|---|---|---|---|---|

**Parts**
| PartID | MachineID | Name | Brand | Model | Note | ImageURL |
|---|---|---|---|---|---|---|

**Images**
| ImageID | MachineID | Section | GroupKey | ImageURL | UploadedAt |
|---|---|---|---|---|---|

- `Section` — `Gallery` or `Internal`
- `GroupKey` — for Gallery: `cover / front / back / left / right / top / internal / others`;
  for Internal: `cover / internal / boiler / pump / pcb / flowmeter / valve / relay / sensor / other`
  (same group keys the wizard already uses in `HK_GALLERY_GROUPS` / `HK_INTERNAL_GROUPS`)

**Documents**
| DocumentID | MachineID | DocType | FileName | FileURL | UploadedAt |
|---|---|---|---|---|---|

- `DocType` — one of `UserManual / ServiceManual / PartsList / WiringDiagram / Firmware / Brochure`


This mirrors `js/machines-data.js` field-for-field, so `Code.gs`'s
`bundleMachine()` reassembles each row set into the exact same nested
object shape the frontend already uses (`specification`, `parts`,
`gallery`, `internalImages`, `documents`) — swapping the seed data for a
real fetch is a small change, not a rewrite.

## Google Drive folder structure

One root folder (e.g. "HILLKOFF Machines"), one subfolder per machine:

```
HILLKOFF Machines/
└── <MachineID> - <Machine Name>/
    ├── Cover/
    ├── Gallery/
    ├── Internal/
    ├── Parts/
    └── Documents/
```

Prefixing with `MachineID` (not just the name, as the original Concept
sketch showed) avoids folder collisions when two machines share a name —
`getMachineFolder()` in Code.gs already does this.

## Deploying Code.gs

1. Create the Google Sheet with the 5 tabs/headers above. Copy its ID from the URL.
2. Create (or reuse) the Drive root folder. Copy its ID from the URL.
3. In the Sheet: **Extensions → Apps Script**, paste in `appscript/Code.gs`.
4. Set `SHEET_ID` and `DRIVE_ROOT_FOLDER_ID` at the top of the file.
5. **Deploy → New deployment → Web app**. Execute as **Me**, access
   **Anyone within [your domain]** (avoid "Anyone" unless the data is meant
   to be public — this is an internal knowledge base).
6. Copy the deployment URL into `js/api-client.js` (`HK_API_URL`).
7. Grant the requested Drive/Sheets permissions on first run.

## Wiring the frontend (already done in this repo)

The frontend is wired to the live backend — `HK_API_URL` in
`js/api-client.js` points at the deployed Web App, and:

- `js/machines-data.js` fetches the full list once per page load
  (`hkBootstrapMachines()`) into an in-memory cache; `getAllMachines()`,
  `getMachineById()`, `searchMachines()`, etc. all read from that cache, so
  they stayed synchronous and none of `dashboard.js` / `machine-detail.js`
  needed to change
- `addMachine(payload)` is now `async` and calls `hkApiCreateMachine`,
  then refreshes the cache
- Every image/photo/document picker in `add-machine.js` uploads to Drive
  immediately via `hkApiUploadFile()` as soon as a file is selected (not
  deferred to final submit), storing the returned Drive URL. This avoids
  ever putting large base64 image data into a Sheet cell, which has a
  ~50,000-character limit and would otherwise cause `createMachine` to
  fail outright on anything but tiny thumbnails
- Because there's no real `MachineID` yet at the time files are picked
  (it's only assigned by `Code.gs` on final save), uploads go into a
  temporary Drive folder named `wizard-<timestamp> - <machine name>`
  instead of `<MachineID> - <name>`. Functionally identical, just not
  renamed to match the final ID — rename manually in Drive afterward if
  that matters to you, or extend `Code.gs` with a "rename folder" action
  if it comes up often enough to automate

If you ever need to point at a different deployment (e.g. after testing),
just change `HK_API_URL` in `js/api-client.js` — nothing else needs to change.

### If you update Code.gs after already deploying it

Apps Script Web App URLs don't change when you edit the script, but the
*running* code only updates when you make a **new deployment version**:
**Deploy → Manage deployments → (pencil icon) Edit → Version: New version
→ Deploy**. Editing `Code.gs` and saving alone is not enough — the live
URL keeps serving whatever version was last deployed until you do this.

### Why POST uses `text/plain`

Apps Script Web Apps don't respond to CORS preflight (`OPTIONS`) requests.
Sending JSON with `Content-Type: application/json` from the browser
triggers a preflight that Apps Script can't answer, so the request fails.
Sending it as `text/plain` keeps it a "simple request" (no preflight) —
Code.gs still parses `e.postData.contents` as JSON normally on the way in.

## Machine evaluation / approval-to-sell workflow

Added to the bottom of the **Internal Structure** tab: five departments
each sign off (typed name + date, no image), then an MD/executive gives
the final "approved to sell" signature. Frontend pieces are already in
place (`js/machines-data.js`, `js/machine-detail.js`, `css/detail.css`),
but `appscript/Code.gs` isn't part of this repo copy, so the backend side
below still needs to be added there by whoever maintains that file.

**New Sheet tab: `Approvals`**

| MachineID | Department | Name | SignedDate | Comment | SubDepartment |
|---|---|---|---|---|---|

- `Department` — one of `technicianDept, technicianAdmin, partsAdmin, sales, purchasing, md`
  (`md` rows are the final MD/executive sign-off; everything else is a
  department signature). One row per signature — `technicianDept` and
  `sales` can have multiple rows for the same `MachineID`.
- `Comment` — free-text evaluation note the signer typed in, for any
  department (including `md`). Optional, can be blank.
- `SubDepartment` — only used on `sales` rows: the salesperson's own
  sub-team/branch (e.g. "ทีมขายภาคเหนือ"), shown after their name on the
  web app. Blank for every other department.
- Required signer counts (enforced client-side, not by the Sheet):
  แผนกช่าง (`technicianDept`) 2, ธุรการช่าง (`technicianAdmin`) 1,
  ธุรการอะไหล่ (`partsAdmin`) 1, ทีมขาย (`sales`) at least 2, แผนกจัดซื้อ
  (`purchasing`) 1, then exactly one `md` row once approved.

**New Code.gs action: `updateApproval`**

Payload: `{ machineId, approval: { departments: { technicianDept: [{name,date,comment}], ..., sales: [{name,date,comment,subDept}] }, mdApproval: {name,date,comment} | null } }`.
Implementation should replace all `Approvals` rows for that `MachineID`
with the full set derived from the payload (simplest: delete existing
rows for that ID, then re-insert one row per signature — same
overwrite-and-rewrite approach `createMachine` likely already uses
elsewhere, so no separate add/remove actions are needed).

**`bundleMachine()`** should also read the `Approvals` tab for each
machine and reassemble it into the same `{ departments: {...}, mdApproval }`
shape so `hkBootstrapMachines()` gets it back exactly as it was saved —
mirrors how `specification`/`parts`/`gallery` are already reassembled.

Until `Code.gs` is updated, `js/api-client.js`'s `hkApiUpdateApproval` call
will fail silently and the frontend falls back to keeping the signatures
in memory for that session only (a toast tells the user this happened) —
so the feature is fully usable for testing today, it just won't survive a
page reload against the live backend yet.

## Editing existing machines — new Code.gs actions

Every part of a machine can now be edited after creation from the
Machine Detail page — **except** the approval workflow above, which
still refuses writes once `mdApproval` is set. These reuse the same 5
tabs, no new Sheet columns beyond what `Approvals` already added:

| Action | Payload | What it does |
|---|---|---|
| `updateMachineInfo` | `{ machineId, category, name, brand, model, type, bcCode, description, coverImageUrl? }` | Overwrites the `Machine` row. `coverImageUrl` is optional — omit to leave it, send `''` to clear it. |
| `updateSpecification` | `{ machineId, specification: {...12 fields} }` | Overwrites the `Specification` row. |
| `updatePart` | `{ partId, name, brand, model, note, imageUrl? }` | Overwrites one `Parts` row by `PartID`. |
| `deletePart` | `{ partId }` | Deletes one `Parts` row. |
| `deleteImage` | `{ machineId, section, groupKey, url }` | Deletes the one `Images` row matching all four fields (an `ImageURL` is unique per Drive file, so this is enough to target exactly one row). |
| `setDocument` | `{ machineId, docType, name, url }` | Replaces whatever `Documents` row exists for that `MachineID` + `DocType` with a new one (delete-then-insert, since each doc type only ever has one active file per machine on the frontend). |
| `deleteDocument` | `{ machineId, docType }` | Deletes the `Documents` row(s) for that `MachineID` + `DocType`. |

`addPart` now also returns `{ ok: true, id: <PartID> }` instead of just
`{ ok: true }` — the frontend needs the generated `PartID` back so a
part added in the same session can immediately be edited or deleted
without a page reload.

## Internal Structure access gate — currently removed

An earlier version of this project gated the Internal Structure tab behind
a passcode (and before that, Google Sign-In). Both were removed to get a
clean, fully-working baseline first — every tab is open right now, same as
every other tab. If you want to re-add a gate later, see the `[2.2.x]`
entries in `CHANGELOG.md` for how both approaches were implemented
(`appscript/Auth.gs` + `js/auth.js`, no longer present in this copy) and
adapt from there.
